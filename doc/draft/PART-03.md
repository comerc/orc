Если рассматривать аналоги Windmill.dev именно в разрезе платформы для разработчиков, объединяющей код, надежные воркфлоу и внутренние интерфейсы, то в 2025 году на рынке выделяются следующие игроки:

1. Kestra

Наиболее прямой конкурент Windmill по философии. Это open-source оркестратор, ориентированный на события (event-driven).

- **Сходство:** Поддерживает декларативное описание (YAML), интеграцию с любыми языками программирования (Python, JS, Shell) и имеет мощный UI для мониторинга.

- **Отличие:** Kestra больше тяготеет к Data Engineering и управлению конвейерами данных, в то время как Windmill позиционирует себя как более универсальная альтернатива Retool + Temporal + Airflow.

2. Prefect (v3.0)

В 2025 году Prefect окончательно превратился из «просто планировщика задач» в полноценную платформу для агентских воркфлоу.

- **Сходство:** Позволяет превратить любую Python-функцию в надежную задачу (Task) с автоматическими ретраями и отслеживанием состояния в облаке.

- **Отличие:** Prefect — это Code-only подход. У него нет визуального билдера интерфейсов (как в Windmill), он фокусируется на прозрачности выполнения кода и динамическом масштабировании.

3. Hatchet

Молодой, но быстрорастущий конкурент, который называет себя «Temporal на Postgres».

- **Сходство:** Решает ту же проблему — выполнение кода с гарантией завершения и низкой задержкой (<20мс).

- **Отличие:** Hatchet специально оптимизирован под AI/ML воркфлоу, предлагая более легкую инфраструктуру, чем Temporal, и более высокую скорость реакции, чем Windmill.

▼ Hatchet vs Temporal

Hatchet is designed to be a general-purpose task orchestration platform -- it can be used as a queue, a DAG-based orchestrator, a durable execution engine, or all three. As a result, Hatchet covers a wider array of use-cases, like multiple queueing strategies, rate limiting, DAG features, conditional triggering, streaming features, and much more.

Temporal is narrowly focused on durable execution, and supports a wider range of database backends and result stores, like Apache Cassandra, MySQL, PostgreSQL, and SQLite.

**When to use Hatchet:** when you'd like to get more control over the underlying queue logic, run DAG-based workflows, or want to simplify self-hosting by only running the Hatchet engine and Postgres.

**When to use Temporal:** when you'd like to use a non-Postgres result store, or your only workload is best suited for durable execution.

▼ Hatchet vs Task Queues (BullMQ, Celery)

Hatchet is a durable task queue, meaning it persists the history of all executions (up to a retention period), which allows for easy monitoring + debugging and powers a bunch of the durability features above. This isn’t the standard behavior of Celery and BullMQ (and you need to rely on third-party UI tools which are extremely limited in functionality, like Celery Flower).

**When to use Hatchet:** when you'd like results to be persisted and observable in a UI

**When to use task queue library like BullMQ/Celery:** when you need very high throughput (\(>10k/s\)) without retention, or when you'd like to use a single library (instead of a standalone service like Hatchet) to interact with your queue.

▼ Hatchet vs DAG-based platforms (Airflow, Prefect, Dagster)

These tools are usually built with data engineers in mind, and aren’t designed to run as part of a high-volume application. They’re usually higher latency and higher cost, with their primary selling point being integrations with common datastores and connectors.

**When to use Hatchet:** when you'd like to use a DAG-based framework, write your own integrations and functions, and require higher throughput (\(>100/s\))

**When to use other DAG-based platforms:** when you'd like to use other data stores and connectors that work out of the box

▼ Hatchet vs AI Frameworks

Most AI frameworks are built to run in-memory, with horizontal scaling and durability as an afterthought. While you can use an AI framework in conjunction with Hatchet, most of our users discard their AI framework and use Hatchet's primitives to build their applications.

**When to use Hatchet:** when you'd like full control over your underlying functions and LLM calls, or you require high availability and durability for your functions.

**When to use an AI framework:** when you'd like to get started quickly with simple abstractions.

К концу 2025 года индустрия ИИ-агентов перешла от стадии хаотичных экспериментов к формированию четких стандартов взаимодействия, которые часто называют «HTTP для ИИ».

Ниже приведены основные стандарты и протоколы, актуальные на 2025 год:

1. Стандарты среды запуска и взаимодействия

Вместо закрытых систем теперь доминируют открытые протоколы, позволяющие агентам из разных фреймворков работать вместе.

- **Model Context Protocol (MCP):** Разработанный Anthropic и поддержанный OpenAI и Google, этот протокол стал «USB-C для данных». Он стандартизирует то, как агент подключается к инструментам (Google Drive, Slack, GitHub) и базам данных, избавляя от необходимости писать уникальный код для каждой интеграции.

- **Agent Communication Protocol (ACP):** Разработка IBM и BeeAI для локальной координации агентов с минимальной задержкой. Он фокусируется на безопасности, приватности и возможности работы в офлайн-средах.

- **Agent-to-Agent Protocol (A2A):** Запущенный Google при поддержке более 50 партнеров, этот протокол предназначен для облачного взаимодействия агентов разных вендоров.

Да, **Open Agentic Schema Framework (OASF)** — это инициатива по созданию единого открытого стандарта для взаимодействия ИИ-агентов, независимо от того, на каком фреймворке они написаны.

Вот ключевые детали на конец 2025 года:

1. Цель и решаемая проблема

OASF разрабатывается сообществом (проект **Agntcy**) для преодоления несовместимости популярных инструментов. На текущий момент каждый фреймворк имеет свою логику:

- **LangGraph/LangChain:** использует графовую структуру и контроль состояний.
- **CrewAI:** ориентирован на ролевое взаимодействие «команд» агентов.
- **AutoGen:** фокусируется на гибких диалоговых паттернах.
- **Semantic Kernel:** корпоративное решение Microsoft для интеграции LLM в ПО.

OASF предлагает общую схему данных, чтобы агент, созданный в LangGraph, мог беспрепятственно обмениваться задачами или инструментами с агентом на AutoGen.

2. Позиция Microsoft: Microsoft Agent Framework

Важно отметить, что Microsoft в 2025 году провела собственную внутреннюю стандартизацию. Компания объединила **AutoGen** и **Semantic Kernel** в единую платформу — **Microsoft Agent Framework (MAF)**.

- **MAF** теперь является официальным фундаментом Microsoft для агентных систем.
- Он поддерживает открытые стандарты, такие как **MCP** (Model Context Protocol) и **OpenAPI**, что концептуально пересекается с целями OASF по обеспечению переносимости агентов.

3. Текущий статус

- **OASF** остается открытой спецификацией (GitHub: agntcy/oasf ), стремящейся стать «интернетом для агентов», где протоколы взаимодействия универсальны.
- Разработчики популярных фреймворков (включая LangChain и CrewAI) постепенно внедряют поддержку общих протоколов, чтобы их агенты могли работать в гетерогенных средах.

**Резюме:** OASF действительно пытается стать «общим языком» для всех перечисленных вами систем, позволяя им взаимодействовать друг с другом в рамках одной экосистемы.

Эволюция оркестрации в 2025 году действительно привела к выделению двух основных паттернов: **Crews** (Команды) и **Flows** (Потоки). Разница между ними заключается в степени автономности и жесткости структуры процесса.

## 1. В чем разница?

| Характеристика | Crews (Команды)                                                                              | Flows (Потоки / Workflows)                                                    |
| -------------- | -------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| Природа        | Автономная и ролевая: агенты сами решают, как выполнить задачу.                              | Детерминированная и событийно-ориентированная: путь выполнения задан заранее. |
| Управление     | Управляются процессом (Sequential, Hierarchical), где агент передает задачу коллеге по роли. | Управляются логикой разработчика (условия if/else, циклы, обработка ошибок).  |
| Гибкость       | Максимальная: агенты могут «импровизировать» в рамках своих навыков.                         | Ограниченная: высокая предсказуемость, важная для продаж щепа и безопасности. |
| Пример         | «Команда маркетинга» (исследователь + автор), где они сами договариваются о черновике.       | Процесс проверки документов: «Шаг 1 -> Проверка -> Если ок, Шаг 2».           |

В современных системах (например, в **CrewAI** 2025 года) эти подходы часто комбинируются: **Flow** может запускать одну или несколько **Crews** как отдельные этапы большого процесса. 💷

## 2. Есть ли оба в OASF?

**Open Agentic Schema Framework (OASF)** — это не движок выполнения (как LangGraph или CrewAI), а **стандарт описания** этих систем. 💷

- **На уровне схемы:** OASF поддерживает оба подхода через универсальные объекты записей (records), аннотированные навыками (**Skills**) и доменами.
- **Crews в OASF:** Описываются через метаданные ролей и коллективные способности агентов, что позволяет другим системам «обнаруживать» готовую команду как единый сервис.
- **Flows в OASF:** Стандартизируются через описание интерфейсов взаимодействия и состояний (**State**), чтобы данные могли бесшовно передаваться между этапами потока, даже если эти этапы реализованы на разных фреймовых. 💷

**Резюме:** OASF спроектирован так, чтобы быть «клеем» для обоих подходов. Он предоставляет структуру данных, которая позволяет описать как автономного агента в команде (Crew), так и его место в жестко заданном алгоритме (Flow). 💷

Аналогия с Temporal очень точна и помогает понять, как агентские системы переходят от «игрушек» к промышленным решениям в 2025 году.

В Temporal есть две базовые сущности: Workflows и Activities. Их можно сопоставить с Flows и Crews (или отдельными агентами) следующим образом:

1. Таблица аналогий

| Сущность в Temporal | Аналог в Agentic (OASF / CrewAI / LangGraph) | Описание роли                                                                                                                                                    |
| ------------------- | -------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Workflow            | Flow (Поток)                                 | **Оркестратор.** Определяет общую логику, последовательность шагов и правила обработки ошибок. Он детерминирован и «знает», что делать дальше.                   |
| Activity            | Crew (Команда) / Agent (Агент)               | **Исполнитель.** Это конкретное действие или «черный ящик» с бизнес-логикой. В случае агентов — это место, где происходит LLM-рассуждение (недетерминированное). |

2. Почему это сравнение работает?

1. Надежность vs Гибкость:

   - В Temporal Workflow гарантирует, что процесс не потеряется (durability), даже если сервер упадет. В агентских системах Flow выполняет ту же роль: он следит, чтобы цепочка рассуждений не прервалась и данные передались от одного агента к другому.
   - **Activity** в Temporal — это место для «грязной» работы (вызовы API, расчеты), которая может упасть и потребовать повторов. В агентской парадигме Crew (Команда) — это такая же «активность», где агенты могут ошибаться, галлюцинировать или превышать лимиты.

1. Детерминизм против Хаоса:

   - Workflow в Temporal обязан быть детерминированным для корректного воспроизведения состояния.
   - Flow в OASF/LangGraph также стараются сделать максимально предсказуемым (код/граф), оставляя всю «творческую автономность» и непредсказуемость на уровне отдельных агентов или их команд (Crews).

1. Место в OASF
   - В 2025 году OASF стремится стандартизировать эти интерфейсы так же, как Temporal стандартизировал распределенные вызовы:
   - **Flows** в схеме OASF описывают, как передается контекст состояния (State).
   - **Crews/Agents** описываются как «ресурсы» или «сервисы» (аналог Activity Workers), которые можно вызвать из любого потока.

**Итог:** Если вы знакомы с Temporal, то думайте о Flow как о надежном сценарии (скрипте), а о Crew — как о наборе автономных работников, которых этот сценарий начинает для выполнения конкретных интеллектуальных задач.

Термин **Durable Execution** (отказоустойчивое исполнение) в 2025 году наиболее плотно ассоциируется с **LangGraph** (частью экосистемы LangChain).

Вот как распределяются эти возможности между указанными фреймворками:

1. **LangGraph (LangChain)** — Прямая поддержка

LangGraph был специально спроектирован с упором на **Durable Execution**.

- **Чекполиты (Checkpointing):** Он автоматически сохраняет состояние графа (state) после каждого шага во внешнее хранилище (например, SQLite, Redis, PostgreSQL).
- **Возобновляемость:** Если выполнение прервалось из-за ошибки сети или падения сервера, процесс можно продолжить ровно с того места, где он остановился, не переделывая предыдущие шаги.
- **Human-in-the-loop:** Поддерживает "паузу" исполнения для ожидания ввода от человека, после чего работа возобновляется с сохранением всего контекста.

2. **AutoGen** — Собственная реализация в v0.4

С выходом версии **AutoGen 0.4** в начале 2025 года архитектура была полностью переписана на событийно-ориентированную (event-driven).

- Теперь используется концепция **Agent Runtime**, которая управляет жизненным циклом агентов.
- Хотя AutoGen традиционно фокусировался на "диалогах", новая архитектура позволяет реализовывать долгоживущие процессы с сохранением состояния, приближаясь к модели Durable Execution.

3. СrewAI — Enterprise-инфраструктура

CrewAI сам по себе является высокоуровневой надстройкой. В 2025 году он предлагает "durable" возможности через CrewAI Enterprise и встроенные механизмы кэширования и обработки ошибок. Однако в плане низкоуровневого управления состоянием графа он менее гибкий, чем LangGraph.

4. Langflow и Flowise — Визуальные слои

Это визуальные редакторы (low-code):

- **Langflow:** В 2025 году активно интегрирует возможности LangGraph, поэтому может поддерживать Durable Execution "под капотом", если поток (flow) построен на базе LangGraph.
- **Flowise:** В основном полагается на стандартные цепочки (chains) LangChain. Если цепочка не использует persistence-слой LangGraph, она не является "durable" (при сбое выполнение начнется сначала).

### Итог

Если ваша задача — создание длительных, надежных рабочих процессов, которые должны выживать после перезагрузки сервера, ваш основной выбор — **LangGraph**.

- **LangGraph:** Есть нативная поддержка "из коробки" через механизм Checkpointers.
- **AutoGen 0.4+:** Поддерживает через новую архитектуру Agent Runtime.
- **Остальные:** Требуют либо внешних инструментов (например, интеграции с Temporal), либо используют LangGraph как базовый движок.

## В чем разница?

| Характеристика | Durable Execution (Temporal / LangGraph) | Durable Streams (ElectricSQL / Protocol)    |
| -------------- | ---------------------------------------- | ------------------------------------------- |
| Где живет      | Бэкенд (серверная логика)                | Транспорт (Server → Client)                 |
| Что защищает   | Выполнение кода и состояние переменных   | Доставку потока данных (токенов, логов)     |
| Проблема сбоя  | Сервер упал во время работы агента       | Вкладка браузера закрылась или Wi-Fi пропал |
| Результат      | Агент продолжит работу на другом сервере | Клиент переподключится и «дочитает» стрим   |

## Применимость для AI в 2025 году

Именно в AI-продуктах эта связка становится критической:

- **Без Durable Execution:** Агент начал сложную задачу (например, анализ 10к документов), сервер перезагрузился — работа потеряна, нужно платить за токены заново.
- **Без Durable Streams:** Агент всё сделал правильно, но у пользователя пропала связь — стрим оборвался, и пользователь видит пустой экран или ошибку, хотя бэкенд всё успешно доделал. ✅

**Итог:** Durable Streams — это идеальное дополнение к Temporal. Если вы строите серьезного агента, вы используете **Temporal/LangGraph** для надежности логики на сервере и **Durable Streams** для надежности отображения этого процесса в UI. ✅

1. Как в Windmill реализован **Durable Execution?**

Windmill — это не просто планировщик задач, это полноценная среда выполнения.

- Устойчивость состояний: Каждый шаг в рабочем процессе (Flow) Windmill сохраняется в базу. Если во время генерации длинного текста LLM или работы агента сервер упадет, Windmill может перезапустить конкретный шаг или продолжить выполнение.

- Длительные процессы: Он идеально подходит для задач, которые длятся часами (например, парсинг сотен страниц для RAG или обучение модели), что технически сложно реализовать в обычных Serverless-функциях.

- Human-in-the-loop: Windmill позволяет ставить процесс на паузу и ждать подтверждения от человека (через сгенерированную форму или UI), сохраняя состояние процесса днями или неделями.

2. Windmill vs Temporal в задачах AI

Хотя оба обеспечивают Durable Execution, Windmill для AI часто удобнее:

- Низкий порог входа: В Temporal нужно описывать рабочие процессы кодом на Java/Go/Python со строгими правилами детерминизма. В Windmill вы просто пишете обычные Python-скрипты или TypeScript-функции.

- Интегрированный UI: Windmill «из коробки» позволяет собрать дашборд для мониторинга агентов. Вы видите, на каком шаге сейчас находится агент, какие токены он стримит и какие ошибки возникают.

- Автоматические API: Любой скрипт или поток в Windmill мгновенно становится эндлоинтом.

3. Windmill как AI-оркестратор

## 4. Сравнение с LangGraph

- LangGraph лучше подходит для цикличной логики (когда агент должен «думать» по кругу: действие → наблюдение → действие).

- Windmill лучше подходит для линейных или разветвленных пайплайнов данных, где критична надежность инфраструктуры, аудит и возможность быстрого построения UI для оператора.

2. Объединить AI-логику с традиционными бизнес-процессами (SQL, API, Slack).

3. Иметь Open Source решение, которое можно развернуть в своем контуре (self-hosted) для безопасности данных.

4. Быстро собрать админку для управления вашими AI-агентами.

В 2025 году это один из самых быстрорастущих инструментов для построения "Self-hosted AI Agents" корпоративного уровня.

## Нативный движок TypeScript (TypeScript Go / tsgo )

Новый движок, получивший кодовое название Corsa (или неофициально tsgo ),
представляет собой полную переработку компилятора для устранения проблем с
производительностью в крупных проектах.

- **Производительность: Первые тесты показывают ускорение проверки типов и**
  сборки проектов в 10 раз. Например, компиляция кодовой базы VS Code
  сократилась с ~78 секунд до примерно 7,5 секунд.

- **Основные функции: Движок отвечает за парсинг, разрешение типов и их**
  проверку. На его базе работает новый нативный LSP (Language Server Protocol),
  обеспечивающий мгновенную автоподстановку и поиск ошибок в редакторах.

- **Совместимость: Microsoft заявляет о 99,99% семантической совместимости с**
  текущим компилятором. Разработчикам не нужно менять свой код, чтобы
  получить прирост скорости.

## Почему был выбран Go?

Команда рассматривала Rust и C#, но остановилась на Go по следующим
причинам:

1. Схожесть структур: Паттерны программирования в Go близки к TypeScript, что
   упростило перенос (портирование) существующей логики компилятора.

2. Управление памятью: Наличие сборщика мусора (GC) в Go критически важно
   для работы со сложными деревьями (AST) TypeScript, которые изобилуют
   циклическими ссылками.

3. Конкурентность: Механизм горутин (goroutines) позволяет легко
   распараллеливать задачи компиляции на все ядра процессора, что было
   невозможно в однопогонном Node.js.

Идея создания аналога Windmill на Go с использованием Inngest в качестве движка выглядит элегантно, но на практике вы столкнетесь с рядом серьезных технических и архитектурных «подводных камней».

Вот основные риски и минусы такого подхода в 2025 году:

1. Архитектурная зависимость от Inngest (Lock-in)

- **Сложность Self-hosting:** Windmill полностью автономен (нужен только Postgres). Inngest же — это либо их облако, либо отдельный сложный сервер, который нужно поднимать рядом. Если вы строите продукт для Enterprise, клиенты часто требуют «один бинарник и база», что со связкой Go + Inngest реализовать сложнее.

- **Непрозрачность стейта:** В Windmill вы можете залезть в Postgres и поправить состояние упавшего шага вручную. В Inngest состояние управляется движком, и прямой доступ к «кишкам» исполнения ограничен.

2. Проблема выполнения произвольного кода (The Runtime Problem)

Windmill — это не только оркестратор, но и среда исполнения (Runtime) для Python и TypeScript.

- **Go — не скриптовый язык:** Чтобы пользователи могли писать логику «на лету» (как в Windmill), вам придется внедрять интерпретатор.

  - _Yaegi_ (Go-интерпретатор) поддерживает не всё и может быть нестабилен.
  - _Wasm_ (Wazero) безопасен, но сложен в разработке (нужно компилировать код пользователя в Wasm перед запуском).

- **Управление зависимости:** В Windmill решение проблем с pip install или npm install уже отлажено годами. В своем Go-решении вам придется заново изобретать велосипед: как изолировать процессы, как ограничивать ресурсы (CPU/RAM) и как кэшировать библиотеки.

3. Ограничения Inngest для специфики AI

- **Размер Payload:** У Inngest есть лимиты на размер данных, передаваемых между событиями (обычно до 4MB). AI-задачи часто оперируют огромными контекстами, PDF-выжимками или массивами эмбардийгов. Вам придется строить внешнее хранилище (S3/Redis) для передачи данных «по ссылке», что усложняет архитектуру.

- **Длительность соединений (Streaming):** Inngest работает по HTTP. Если вы хотите сделать честный Durable Stream (токены из LLM прямо в клиент), то проксировать этот поток через Inngest и Go-бэкенд так, чтобы он не отвалился по таймауту — задача нетривиальная.

4. Отсутствие "Visual Flow" и экосистемы

- **UI-инфраструктура:** Windmill предоставляет готовый конструктор форм и графов. Создание визуального редактора, который корректно малится на Go-код и события Inngest, займет 70% времени разработки.

- **Интеграции (Hub):** Главная ценность Windmill — сотни готовых скриптов для Slack, S3, Postgres, OpenAI. Вам придется либо писать их самому, либо просить пользователей делать это с нуля.

5. Риск производительности при высокой нагрузке

- **Inngest использует опрос (polling)** или **webbook-модель** для доставки событий. При взрывном росте количества микро-шагов в AI-агенте (например, агент в цикле делает 100 мелких действий) накладные расходы на HTTP-вызовы между вашим Go-приложением и Inngest могут создать заметную задержку (latency) по сравнению с нативным Rust-ядром Windmill.
