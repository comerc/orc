Для изоляции агентов под управлением Hatchet на Go, вы реализуете **Go-воркер**, который для каждой задачи порождает изолированный процесс.

**Архитектура в связке с Hatchet:**

1. **Hatchet Engine (Go):** Принимает запрос на запуск агента.

2. **Hatchet Go Worker:** Получает задачу от Engine.

3. Внутри воркера вы используете **microsoft/typescript-go** для быстрой проверки и транспиляции TS-кода агента.

4. Затем воркер вызывает **nsjail + Deno (или nsjail + QuickJS)**, как мы обсуждали ранее.

5. **Изоляция:** Каждый агент запускается в отдельном инстансе **nsjail**. Hatchet следит за таймаутами и повторами (retries).

---

### Реализует ли Hatchet рентайм сам?

**Нет.** В репозитории Hatchet нет встроенной песочницы для произвольного пользовательского кода. Его задача — надежная доставка задачи до воркера и управление очередями.

---

### Почему Hatchet + Go + nsjail/Deno — это победа:

1. **Масштабируемость:** Hatchet на Go невероятно быстрый и легкий. Вы можете запускать тысячи воркеров.

2. **Отказоустойчивость:** Если nsjail прибьет процесс агента из-за превышения памяти, Hatchet зафиксирует это как ошибку шага и позволит вам легко перезапустить задачу или оповестить пользователя.

3. **Контроль из Go:** Весь управляющий код (Hatchet Worker) написан на Go, что избавляет вас от «винегрета» в логике оркестрации.

---

### Итог:

Hatchet даст вам **инфраструктуру** (очереди, события, логи, retry-политики), но **механику изоляции** (nsjail + выбор движка) вам нужно будет прикрутить к Hatchet-воркеру самостоятельно.

Если вы хотите увидеть примеры воркеров Hatchet на Go, посмотрите их официальную документацию в разделе Go SDK, но помните: вызов nsjail внутри функции воркера — это ваша кастомная логика.

Идя по пути Б с Hatchet в качестве оркестратора, вы создаете архитектуру, максимально близкую к промышленным PaaS-решениям (вроде Vercel или Supabase Edge Functions).

Вот как правильно реализовать этот «Runner» на Go в конце 2025 года, чтобы это было надежно и эффективно:

1. Анатомия вашего Runner (Hatchet Worker на Go)

Ваш Go-процесс будет «умной прослойкой». Он не просто запускает `nsjail`, а управляет жизненным циклом агента.

- **Шаг 1: Валидация (microsoft/typescript-go).** В 2025 году это ваш первый фильтр. Как только Hatchet передает задачу воркеру, вы прогоняете код через Go-компилятор TS. Если там синтаксические ошибки или попытки импорта запрещенных модулей — вы сразу возвращаете Hatchet статус FALLED без запуска тяжелых песочниц.

- **Шаг 2: Подготовка RootFS.** Вместо копирования файлов для каждого запуска, используйте OverlayFS. Основные файлы Deno и стандартные библиотеки лежат в `lowerdir` (только чтение), а код агента и его временные файлы — в `upperdir`.

- **Шаг 3: Запуск через nsjail.** Вы вызываете `nsjail` из Go, используя контекст (`context.Context`) с таймаутом. Это гарантирует, что если Hatchet отменит задачу, процесс в `nsjail` будет немедленно убит.

2. Почему это лучше реализации GitLab Runner?

GitLab Runner универсален, но из-за этого избыточен. Ваш кастомный Runner на Hatchet будет:

1. **Быстрее:** Вам не нужно скачивать Docker-образы. Deno в `nsjail` стартует за 20–50 мс.

2. **Дешевле по памяти:** Вы можете запускать сотни агентов на одном сервере, так как они делят общие системные библиотеки через `readonly` монтирование в `nsjail`.

3. **Глубокая интеграция:** Ваш Go-воркер может перехватывать `stdout` агента в реальном времени и стримить логи напрямую в Hatchet или вашу БД через gRPC.

3. Пример структуры функции воркера на Go:

```go
func (w *AgentWorker) ExecuteTS(ctx worker.JobContext) error {
    input := &AgentInput()
    ctx.WorkflowInput(input)

    // 1. Транспиляция (TypeScript 7.0 Go API)
    jsCode, err := tsgo.Transpile(input.SourceCode)
    if err != nil {
    return fmt.Errorf("TS syntax error: %w", err)
    }

    // 2. Формирование команды nsjail
    cmd := exec.CommandContext(ctx.Done(), "nsjail",
    "---config", "/etc/nsjail/deno.cfg",
    "---", "/usr/bin/deno", "run", "---no-remote", "--", // чтение из stt
    }

    // 3. Передача кода и сбор логов
    cmd.Stdin = strings.NewReader(jsCode)
    output, _ := cmd.CombinedOutput()

    // 4. Возврат результата в Hatchet
    ctx.StepOutput(map[string]interface(){
    "result": string(output))
    return nil
}
```

4. На что обратить внимание в 2025 году:

1. Холодный vs Горячий запуск: Если агенты запускаются очень часто, держите «пул» заранее запущенных процессов nsjail, которые ждут код через именованный канал (pipe). Это снизит задержку до <10 мс.

1. Общение Агент -> Двигатель: Если агенту нужно вызвать ваш API (например, «спроси что-то у БД»), не давайте ему доступ к сети. Вместо этого пробросьте в nsjail Unix Domain Socket. Ваш Go-воркер будет слушать этот сокет и работать как безопасный прокси.

1. Deno 2.x: Используйте именно вторую версию Deno, так как в ней значительно улучшена работа с ресурсами и упрощена структура каша, что важно для монтирования в nsjail.

Вердикт: Связка Hatchet (Оркестрация) + Go (Логика/TS-компиляция) + nsjail (Изоляция) + Deno (Исполнение) — это архитектурный "State of the Art" для запуска AI-агентов на конец 2025 года. Она дает безопасность уровня облачных провайдеров при минимальных затратах на инфраструктуру.

если вы строите современный рантайм для AI-агентов на Go и хотите избежать «винегрета» из технологий, сохранив изоляцию и скорость, в конце 2025 года есть три серьезных альтернативы связке `nsjail + Deno`.

### 1. WebAssembly (Wasm) + Wazero (Самый «чистый» Go-путь)

Это сейчас главный тренд для Edge-вычислений и AI-агентов.

- **Как это работает:** Вы транспилируете TypeScript в Wasm (используя проект **Javy** от Shopify или **Extism**). Затем запускаете этот Wasm внутри своего Go-приложения с помощью библиотеки **Wazero**.

- **Почему это круто:**

  - **Wazero** написан на чистом Go (Zero CGO). Никакого C++, Rust или внешних бинарников.
  - **Изоляция:** Wasm по определению работает в песочнице. Агенту не нужно ядро Linux или `nsjail`, он физически не может выйти за пределы памяти, выделенной ему в Go.
  - **Скорость:** Запуск происходит за микросекунды.

- **Минус:** Ограниченная поддержка некоторых Node.js библиотек, которые используют нативные вызовы.

### 2. Firecracker (Микро-BM or AWS)

Если `nsjail — это забор, то Firecracker — это отдельный бункер.

- **Как это работает:** Вместо изоляции процессов (namespaces), Firecracker запускает микроскопические виртуальные машины (MicroVM) менее чем за 100 мс.

- **Для Go:** Существует отличный SDK на Go (**firecracker-go-sdk**), который позволяет вашему движку управлять сотнями таких BM.

- **Почему это круто:** Это самая высокая степень безопасности. Даже если агент найдет O-day уязвимость в V8 (Deno/Вun) и уязвимость в ядре Linux, он все равно останется внутри виртуальной машины.

- **Минус:** Требует поддержки виртуализации (KVM) на сервере (не заведется внутри обычного VPS без вложенной виртуализации).

РaaS-решениям (вроде Vercel или Supabase Edge Functions) - расскажи про них (основное о ...

Индустрия PaaS-решений (Vercel, Supabase, Cloudflare Workers) в 2025 году окончательно разделилась на два технологических лагеря в вопросе запуска TypeScript: Isolate-based (на базе движка V8) и MicroVM-based (на базе Firecracker).

Вот как они реализованы «под капотом»:

1. Cloudflare Workers & Vercel Edge (Isolate-based)

Эти платформы не используют Docker или виртуальные машины для каждой функции. Они используют V8 Isolates.

- **Реализация:** Внутри одного процесса операционной системы запускаются сотни «изолятов» движка V8. Каждый изолят — это отдельная песочница с собственной памятью и кучей (heap), но они делят один и тот же исполняемый код движка.

- **Транспилипция:** Весь TypeScript превращается в JavaScript на этапе деплов (используя сверхбыстрые инструменты вроде **esbuild** или **SWC** на Rust).

- **Безопасность:** Изоляция происходит на уровне самого движка V8. Это дает невероятную скорость запуска (Cold Start < 5 мс), но не защищает от критических уязвимостей в самом V8.

- **Runtime:** Они используют собственные реализации API (например, workerd or Cloudflare), которые максимально облегчены и не поддерживают тяжелые части Node.js.

2. Supabase Edge Functions (Deno-based)

Supabase пошла по пути использования Deno, что ближе к вашей идее.

- **Реализация:** Каждая функция — это по сути вызов инстанса Deno. В ранних версиях они использовали Docker, но в 2025 году перешли на более легкую архитектуру.

- **Изоляция:** Supabase использует **основной процесс на Go** (их собственный edge-runtime ), который управляет пулом рабочих процессов Deno. Для изоляции системного уровня они используют комбинацию примитивов Linux (аналогичных nsjail ) и кастомных планировщиков.

- **TypeScript:** Поскольку это Deno, транспилипция происходит «на лету» внутри рентайма, что упрощает деплой для пользователя.

# 3. AWS Lambda & Fly.io (MicroVM-based)

Это более «тяжелый», но максимально безопасный подход.

- **Реализация:** Используется **Firecracker** (написан на Rust). Для каждого запроса (или группы запросов) создается крошечная виртуальная машина с обрезанным ядром Linux.
- **Изоляция:** Это аппаратная виртуализация. Агент находится внутри своей ОС. Даже взлом ядра этой ОС не дает доступа к хосту.
- **Runtime:** Внутри MicroVM может крутиться что угодно: Node.js, Bun или Deno.

## Ключевые «фишки», которые вам стоит заимствовать у PaaS:

1. **Zero-Trust Networking:** Как и в Supabase, не давайте агенту доступ к localhost вашего сервера. В nsjail это делается через полную изоляцию сетевого стека (~N).

2. **Streaming Logs:** Реализуйте перехват stdout/stderr в Go-воркере так, чтобы логи улетали в Hatchet по частям, не дожидаясь завершения скрипта. Пользователи AI-агентов любят видеть «мысли» агента в реальном времени.

3. **Read-only RootFS:** Это стандарт для всех PaaS. Код агента должен лежать в папке, куда он сам не может писать. Все записи — только в /tmp, который очищается после выполнения.

4. **Graceful Kill:** Используйте механизмы Hatchet для жесткого убийства процесса nsjail по таймауту. PaaS-решения никогда не позволяют функции «висеть» бесконечно.

**Итог:** Ваша архитектура на **Hatchet + Go + nsjail + Deno** фактически повторяет путь **Supabase**, но дает вам больше контроля, так как вы сами управляете процессом на Go. В 2025 году это считается «золотым стандартом» для self-hosted платформ исполнения кода [1][2][3][4].

Для реализации системы «доверия» в рантайме на базе Go + Hatchet + nsjail +
**Deno в 2025 году используется многоуровневый подход. Вы можете гибко менять**

Вот как это реализовать технически:

### 1. Профили изоляции в nsjail

Вместо одного конфига nsjail создайте несколько профилей (Policy-based
isolation). Ваш Go-воркер будет выбирать конфиг на основе метаданных агента из
Hatchet.

- **Профиль «Zero Trust» (для чужих/новых агентов):**

○ Сеть: Полностью отключена ( –N ).

○ Файловая система: Только чтение ( readonly ), кроме пустого /tmp (в RAM).

○ Системные вызовы: Жесткий белый список через `seccomp` .

○ Лимиты: Минимальный CPU и RAM (например, 128MB).

- **Профиль «Trusted» (для ваших внутренних агентов):**

○ Сеть: Доступ к определенным внутренним API или базам данных.

○ Файловая система: Доступ к папке с кашем или специфическим ресурсам.

○ Системные вызовы: Разрешены `io_uring` или другие быстрые вызовы для
производительности.

○ Лимиты: Расширенные карты на ресурсы.

### 2. Подмена рантайма (Deno Permissions)

Поскольку вы используете Deno, вы можете управлять доверием на уровне самого
рантайма, даже не меняя настройки `nsjail` :

- **Недоверенный:** `deno run —no—remote —allow—none script.ts` (запрещено
  всё).

- **Доверенный:** `deno run —allow—net=api.yourserve.com —allow—read=/data`
  script.ts .

Ваш Go-воркер просто динамически формирует флаги запуска Deno на основе
статуса доверия.

### 3. Уровни исполнения (Multi-tier Runtime)

Вы можете пойти дальше и физически запускать доверенных и недоверенных
агентов в разных средах:

1. Untrusted: Запуск в `nsjail` внутри gVisor (двойная изоляция, медленно, но
   максимально безопасно).

2. Trusted: Запуск в обычном `nsjail` (быстро, нативно).

4. Реализация в архитектуре Hatchet

В Hatchet это реализуется через Worker Tags или разные Queues (очереди):

- Вы запускаете два типа воркеров на Go: worker-secure и worker-high-perf .

- Воркер worker-secure настроен на жесткий nsjail .

- В Hatchet в определении Workflow вы указываете:

```go
// Если агент помечен как доверенный, задача уходит на быстрый воркер if agent.IsTrusted {
    ctx.Dispatch("high-perf-queue", task)
} else {
    ctx.Dispatch("secure-sandbox-queue", task)
}
```

5. Безопасный мост (Privileged Bridge)

Для доверенных агентов часто нужен доступ к «своим» данным. Не давайте им логины/пароли от БД напрямую.

- **Реализация:** Go-воркер создает Unix Domain Socket внутри nsjail .

- Доверенный агент пишет в сокет запрос (например, JSON).

- Go-воркер (вне песочницы) проверяет права, сам идет в БД и возвращает агенту только нужные данные.

- Для недоверенных агентов этот сокет просто не создается.

### 3. Межъязыковой интерфейс (The Bridge)

Чтобы агенты на разных языках могли общаться с вашим движком одинаково,
используйте Unix Domain Sockets + JSON-RPC.

- Внутри `nsjail` (для любого языка) монтируется один и тот же сокет
  /tmp/agent.sock .

- Вы предоставляете микро-библиотеки (SDK) для TS, Python и Go, которые просто
  пишут в этот сокет.

- Ваш Go-воркер Hatchet слушает этот сокет. Ему всё равно, на каком языке
  написан агент, — он получает стандартизированный JSON.

### 4. Особенности для Python и Go в nsjail (2025)

- **Python: Самая большая проблема — site-packages . B nsjail нужно**
  монтировать стандартную библиотеку Python в режиме readonly . Используйте
  виртуальные окружения ( venv ), чтобы изолировать зависимости разных агентов.

- **Go: Поскольку Go требует компиляции, процесс будет двухэтапным.**

1. Этап 1: go build вне песочницы (или в отдельной «сборочной» песочнице).

2. Этап 2: Запуск чистого бинарника в nsjail без доступа к исходникам и
   компилятору.

### 5. Архитектура в Hatchet

В Hatchet вы можете использовать Labels для воркеров:

- Некоторые воркеры могут иметь тег runtime:all (у них установлены и Deno, и
  Python).

- Некоторые — только runtime:go (для высоконагруженных задач).

### Итоговая схема:

1. Hatchet — управляет очередью и логикой (Workflow).

2. Go-воркер — принимает задачу, определяет язык.

3. TS-Go компилятор (для TS) или Go компилятор (для Go) — готовит код.

4. nsjail — запускает соответствующий рентайм (Deno/Python/Binary).

5. Unix Socket — обеспечивает единый канал связи агента с вашей платформой.

### 1. Производительность (Плюс для Bun)

- **Холодный старт: Bun стартует еще быстрее, чем Deno. Если ваши агенты**

выполняют микро-задачи (например, атомарный ответ на сообщение), Bun
сократит задержку на 10–20 мс.

- **Транспиляция: Bun имеет самый быстрый встроенный транспилятор TypeScript.**

Если вы решите не использовать microsoft/typescript-go на стороне Go, Bun
справится с превращением TS в JS быстрее всех конкурентов прямо внутри
песочницы.

### 2. Изоляция и nsjail (Главный риск)

Bun — это «спортивный болид», который оптимизирован под современные функции
ядра Linux:

- **io_uring: Bun активно использует этот механизм для сверхбыстрого I/O. Однако**

nsjail по умолчанию (из соображений безопасности) блокирует многие вызовы
io_uring .

- **Проблема: Чтобы Bun работал стабильно внутри nsjail, вам придется**

существенно «расслабить» фильтры системных вызовов (вессomp профиль). Это
**снижает общую безопасность системы. Если агент найдет дыру в реализации**
io_uring в ядре, он сможет сбежать из песочницы. Deno в этом плане ведет себя
более консервативно и «дружелюбнее» к жестким ограничениям.

### 3. Экосистема (Жирный плюс для Bun)

- **Совместимость с npm: В 2025 году Bun практически идеально поддерживает**

Node.js API. Если ваши AI-агенты должны использовать сложные библиотеки
(например, для работы с PDF, специфические драйверы БД или тяжелые SDK), Bun
запустит их без ошибок, с которыми Deno все еще иногда сталкивается.

4. Внутренний движок (V8 vs JavaScriptCore)

- **Deno использует V8 (Google).** V8 — это стандарт индустрии с огромным количеством инструментов для ограничения памяти и отладки.

- **Bun использует JavaScriptCore (Apple).** Он быстрее в некоторых сценариях запуска, но потребляет больше памяти «в покое». В контексте **Hatchet**, где у вас могут быть тысячи задач, повышенное потребление памяти каждым инстансом Bun может увеличить расходы на инфраструктуру.

5. Потеря встроенной безопасности

- **Deno:** Имеет флаги —allow-net , —allow-read . Это ваш второй слой защиты внутри nsjail .

- **Bun:** Не имеет встроенной системы разрешений. Если агент пробил nsjail, у него сразу есть все права процесса. С Deno ему пришлось бы пробивать еще и песочницу рантайма.

В 2025 году ответ однозначный: **да, это критически важно**, особенно если ваш продукт — это платформа для AI-агентов.

1. Специфика AI-агентов (Prompt Injection)

В отличие от обычного бэкенда, где код пишет ваш разработчик, AI-агент может сгенерировать вредоносный код «случайно» или под воздействием Prompt Injection.

Только за последние пару лет в V8 было найдено несколько критических уязвимостей типа RCE (Remote Code Execution), связанных с компонентами _Maglev и Turbofan_.

- V8 — это 10+ миллионов строк кода на C++. Это делает его подверженным ошибкам управления памятью.
- Если вы используете только V8 (как Cloudflare), вы полностью зависите от того, как быстро Google выпустит патч, а вы его примените.

# 3. nsjail как «второй эшелон» (Defense in Depth)

Ваша связка **nsjail + Deno** — это классическая многослойная защита:

1. **Слой V8 (Deno):** Защищает от обычного несанкционированного доступа к памяти внутри процесса.

2. **Слой nsjail (Linux Namespaces):** Даже если агент «пробил» V8 и получил права процесса Deno, он оказывается в пустой комнате:

3. Он не видит чужих процессов.

4. Он не видит файловую систему хоста.

5. Он не может открыть сетевое соединение (если -N включен).

6. Он не может вызвать ежеседля запуска стороннего бинарника.

# 4. Почему PaaS-гиганты могут позволить себе только V8?

Cloudflare или Vercel используют только V8 Isolates, потому что:

- У них работают сотни инженеров по безопасности, которые пишут собственные патчи для V8.

- У них есть кастомные мониторинги системных вызовов на уровне всей сети.

- У них **огромные юридические бюджеты** и страховки.

Для частного проекта или стартапа в 2025 году риск «побега» из V8 без дополнительного слоя вроде nsjail может означать полную компрометацию данных всех клиентов.

Использование **Deno 2** действительно закрывает вопрос _выполнения_ TypeScript, но в архитектуре профессиональной платформы для AI-агентов на **Go**, вышедший в конце 2025 года **microsoft/typescript-go (ts-go)**, играет роль «охранника на входе».

Вот 3 конкретные причины, почему вам всё равно стоит использовать ts-go в связке с Deno:

1. Молниеносная валидация «на берегу» (Pre-flight Check)

Если вы просто отправите код агента в Deno внутри nsjail, и в коде будет ошибка (например, опечатка в типе), вы узнаете об этом только тогда, когда:

1. Hatchet выделит ресурсы.

2. Go-воркер создаст изоляцию nsjail.

3. Запустится процесс Deno.

4. Deno распарсит код и выдаст ошибку.

С ts-go : Ваш основной движок на Go проверяет синтаксис и типы кода агента до запуска песочницы. Если код «битый», вы мгновенно возвращаете ошибку в Hatchet, экономя ресурсы процессора и время жизни воркера. Это в 10–50 раз быстрее, чем запуск Deno для проверки.

2. Безопасный статический анализ (Security Guard)

Deno внутри nsjail защищает систему, но ts-go защищает вашу логику.

- **Запрещенные паттерны:** Вы можете использовать ts-go для анализа AST (дерева кода). Например, если вы не хотите, чтобы агенты использовали eval() или определенные импорты, ts-go найдет их на этапе компиляции в Go.

- **Генерация метаданных:** ts-go может вытащить из кода агента список функций или требуемых разрешений. Вы можете автоматически понять: «этому агенту нужен доступ к сети», и только тогда добавить флаг —allow-net в Deno.

# 3. Трансформация кода (Sanitization)

Иногда код AI-агента нужно «подправить» перед запуском:

- Добавить обертки для логирования.
- Внедрить глобальные переменные или SDK.
- Скрыть детали реализации вашей платформы. Поскольку ts-go работает на Go, вы делаете эти манипуляции в памяти вашего основного приложения с огромной скоростью, передавая в Deno уже «чистый» и подготовленный JavaScript.

---

## Итоговая цепочка обработки в 2025 году:

1. **Пользователь/AI** присылает TS-скрипт.

2. **Go Engine ( ts-go ):**

   - Проверяет типы (Type-check).
   - Проверяет безопасность (Lint/AST scan).
   - Транспилирует в JS.

3. **Hatchet:** Ставит задачу в очередь.

4. **Go Worker:** Запускает **Deno 2** в **nsjail**, скармливая ему уже готовый, проверенный JS.

**Резюме:** Deno — это **исполнитель (runtime)**, а ts-go — это **контролер (compiler/analyzer)**. В серьезных системах исполнения кода (PaaS) они всегда работают в паре, чтобы обеспечить максимальную скорость реакции и безопасность хоста.
