# Подробный разбор Restate и как его портировать на Go

Ниже — систематизированный разбор того, **что именно делает Restate** и **как это реализовывать при портировании серверной части на Go**. Я исхожу из открытой документации и структуры репозиториев Restate‑Server на Rust и Go‑SDK.

---

## 1. Что такое Restate и что именно нужно портировать

Restate состоит из двух больших частей:

1. **Сервер (runtime)**  
   Одно бинарное приложение, написанное на Rust, которое:

   - принимает запросы (Ingress),
   - маршрутизирует их по партициям (partitioning),
   - ведёт **распределённый журнал (log)**,
   - выполняет **обработку шагов и управление состоянием** в воркерах,
   - управляет **метаданными и ролями через встроенный Raft‑контур** и снапшоты в S3 [1][2].

2. **SDK для языков** (TypeScript, Java/Kotlin, Python, Go, Rust)  
   SDK позволяют писать «обычные» обработчики, а Restate прозрачно добавляет:
   - durable execution,
   - state,
   - timers,
   - resilient RPC [1][3].

У Restate уже **есть Go‑SDK** (`github.com/restatedev/sdk-go`), который даёт:

- определение обработчиков и сервисов,
- генерацию кода из protobuf (`protoc-gen-go-restate`),
- ingress‑клиенты и тестовую инфраструктуру [3].

**Портирование на Go** почти наверняка означает:  
переписать **серверный runtime** (Rust‑бинарник `restate-server`) на Go, при этом **максимально сохранив протоколы и семантику**, чтобы существующие SDK (включая Go) могли работать без переделок.

## 2. Ключевые функции Restate и их технический смысл

### 2.1. Durable Execution (устойчивое исполнение)

Суть:

- Любое выполнение «обработчика» (handler) рассматривается как **последовательность шагов**:
  - чтение/запись состояния,
  - вызовы других сервисов,
  - постановка таймеров,
  - ожидание внешних событий.
- **Каждый шаг и его результат записываются в журнал** (per‑invocation journal).
- Если процесс или нода падает:
  - при перезапуске Restate **проигрывает журнал** и:
    - **пропускает уже завершённые шаги** (используя записанные результаты),
    - продолжает исполнение с первого незавершённого шага [1][2].

Фактически это «distributed durable async/await»:

- ваш код остаётся императивным,
- runtime отвечает за то, чтобы шаги не повторялись, а вся цепочка дошла до конца хотя бы один раз.

### 2.2. Resilient RPC

- Restate **проксирует все вызовы** между сервисами через свой сервер:
  - повторяет их при сбоях транспорта или нод,
  - гарантирует отсутствие дубликатов («exactly‑once по смыслу»),
  - ведёт полную трассировку цепочек вызовов [1].

Это означает:

- никакие отдельные брокеры/очереди не нужны — их роль берёт на себя Restate [1][2].

### 2.3. Согласованное состояние (Virtual Objects и Workflows)

Restate даёт:

- Встроенное key‑value хранилище **на уровне сущности**:
  - у каждого виртуального объекта и воркфлоу свой namespace состояния,
  - состояние **журналируется вместе с шагами выполнения**,
  - обеспечивается **single‑writer‑гарантия** на ключ (нет гонок при изменении) [1].

Сервисы при этом _логически статeless_:

- state и журнал живут в Restate‑Server,
- при каждом вызове нужный state подтягивается с сервера и после шага записывается обратно [1].

### 2.4. Suspensions на FaaS

- На FaaS (AWS Lambda и т.п.) Restate умеет:
  - «замораживать» исполнение во время ожидания:
    - ответа пользователя,
    - внешнего события,
    - долгого таймера,
  - и **возобновлять** с нужного шага без «простоя» функции (никакого платного простоя по тайм‑ауту) [1][2].

### 2.5. Архитектура сервера

Документация описывает Restate как:

- **Partitioned, log‑centric runtime**:

  - ключи (workflowID, virtualObjectKey, idempotencyKey) хешируются в партиции,
  - каждая партиция обрабатывается своим процессором (partition processor),
  - все события по партиции идут в **реплицируемый журнал** [2].

- **Ключевые компоненты** [2]:
  - **Ingress**
  - **Durable Log (Bifrost)**
  - **Partition Processor**
  - **Control Plane & Metadata (Raft)**
  - **Snapshotting в S3**
  - **RocksDB‑кэш состояния** на воркерах.

## 3. Подробная архитектура Restate‑Server (важно для порта на Go)

### 3.1. Ingress

**Назначение**:

- Входная точка для:
  - клиентских HTTP‑/gRPC‑вызовов,
  - внутренних вызовов между сервисами.
- Определяет:
  - какой сервис/handler вызывается,
  - какой ключ (workflowID / virtualObjectKey / idempotencyKey),
  - по какому алгоритму их отнести к партиции (hash) [1][2].
- Направляет запрос лидеру нужной партиции (лидерство узнаётся через control plane).

**Что нужно сделать на Go**:

- HTTP‑сервер (например, net/http + mux, gin, chi) или gRPC‑server.
- Логика:
  - парсинг пути/заголовков → определение целевого сервиса/handler,
  - вычисление партиции по ключу (например, `crc32` / `xxhash`),
  - запрос к metadata‑слою: «кто лидер партиции N?»,
  - маршрутизация запроса (RPC или внутренняя шина) на этот worker.

---

### 3.2. Durable Log (Bifrost)

**Что делает** [2]:

- Для каждой партиции:
  - есть **лидер‑сиквенсер**, который задаёт порядок событий,
  - события **реплицируются** на несколько реплик (log‑servers),
  - запись считается **committed**, когда кворум реплик подтвердил добавление.
- Журнал **сегментирован**:
  - есть активный сегмент, куда пишутся новые записи,
  - при переиндексации/смене лидера сегмент закрывается, заводится новый,
  - это позволяет:
    - быстро переключать лидерство,
    - менять конфигурацию без копирования данных [2].

**Go‑реализация (упрощённый план)**:

1. **Структура логического журнала**:
   - `SegmentedLog` с:
     - каталогом сегментов (`/var/lib/restate/partition-<id>/segment-<seq>.log`),
     - индексом `offset -> (segment, fileOffset)`.
2. **Запись**:
   - `Append(record []byte)`:
     - сериализация (protobuf),
     - запись в активный сегмент,
     - `fsync`/batch‑sync для устойчивости.
3. **Репликация**:
   - Выбор:  
     а) использовать **etcd/raft** как основу лога (он уже реализует RAFT‑лог),  
     б) реализовать отдельный лог и использовать Raft только для метаданных.
4. **Чтение (tailing)**:
   - Workers читают записи по индексу и смещению,
   - применяют их к состоянию, двигают `LastAppliedIndex`.

---

### 3.3. Partition Processor (Worker)

**Роль** [2]:

- Для каждой партиции есть один **лидер‑процессор** и (опционально) фолловеры.
- Лидер:
  - «подписан» на хвост журнала,
  - применяет записи:
    - вызывает обработчики через двунаправленный стрим,
    - ведёт материализованный state‑кэш (RocksDB),
    - управляет timers, promises, idempotency‑метаданными [2].
- Фолловеры держат такой же state‑кэш «вровень» с логом, чтобы можно было быстро переключить лидерство.

**Go‑реализация**:

- Типично:

```go
type PartitionWorker struct {
    PartitionID   int
    Log           LogReaderWriter
    StateCache    KVStore           // Badger/Pebble
    JournalIndex  uint64            // LastAppliedIndex
    // таймеры, локальные очереди, канал для shutdown и т.п.
}
```

- Цикл работы:
  1. На старте:
     - загрузить последний снапшот (если есть),
     - дочитать лог до актуального состояния (`replay`).
  2. Основной цикл:
     - `ReadSince(JournalIndex)` → новая порция записей,
     - для каждой:
       - десериализовать,
       - если это:
         - новый invocation → создать контекст, вызвать handler,
         - шаг execution → применить к состоянию (Get/Set/Call/Sleep),
         - таймер → запланировать wakeup,
         - метаданные idempotency → обновить.
       - обновить `JournalIndex` и state‑кэш.
  3. Фолловер:
     - делает то же, что лидер, но **не вызывает handlers**, а только применяет записи к кэшу.

---

### 3.4. Control Plane (метаданные + Raft)

**Функции** [2]:

- Хранит:
  - список нод и их роли,
  - mapping `партиция → (лидер, реплики)`,
  - описания сегментов логов,
  - epoch/term для каждого лидера.
- Использует **встроенный Raft**, но только для этого «тонкого» слоя;  
  **данные пользователя в Raft не хранятся** — они живут в Bifrost‑логе.

**При сбоях** [2]:

- контроллер:
  - через heartbeats/gossip видит отвалившийся лидер,
  - «запечатывает» текущий сегмент журнала (sealing),
  - выбирает нового лидера, создаёт новый head‑segment,
  - обновляет метаданные; ingress узнаёт новый routing.

**Что делать в Go**:

- Взять, например, **go‑etcd/raft**:
  - поднять in‑process Raft с:
    - cluster конфигом,
    - персистентным журнальчиком на диске (отдельным от Bifrost).
- Поверх Raft реализовать `MetadataStore`:
  - `GetPartitions()`, `GetLeader(partID)`, `UpdatePlacement(...)`.
- Ingress и логи/воркеры подписать на изменения метаданных:
  - либо через watch,
  - либо периодический pull.

---

### 3.5. Durability и Snapshots

**Модель хранения** [2]:

- Источник правды — всегда **реплицируемый журнал**.
- RocksDB‑кэш — **производный**, его можно восстановить из лога.
- Чтобы **ограничить время восстановления**, регулярно:
  - делают снапшот состояния партиции (RocksDB),
  - сохраняют его в объектное хранилище (S3),
  - после успешного снапшота лог **обрезают** до точки снапшота.

**Go‑реализация**:

- Для каждого воркера/партиции по расписанию:
  1. Остановить приём записей в кэш (короткий stop‑the‑world для конкретной партиции).
  2. Зафиксировать текущее состояние Badger/Pebble (есть API для снапшотов).
  3. Упаковать снапшот в архив (tar+gz) и отправить в S3/MinIO.
  4. Записать в control plane:
     - `snapshotIndex`, `snapshotLocation`.
  5. Лог до `snapshotIndex` можно обрезать (log compaction).

---

### 3.6. Роли и деплоймент

Из архитектурного описания [2]:

- Узлы могут иметь различные роли:
  - **metadata server** – Raft‑метаданные,
  - **ingress** – HTTP‑вход,
  - **log server** – хранит и реплицирует лог,
  - **worker** – обрабатывает партиции.

Развёртывание:

- Можно иметь всё в одном процессе (для dev):
  - один бинарник с ролями `[metadata, ingress, log, worker]`.
- В проде:
  - обычно разносить роли по нодам/подам Kubernetes.

**На Go** удобно реализовать:

- общий `main` и `--roles=ingress,worker` для выбора нужного набора горутин.

## 4. Go‑SDK и интеграция с сервером на Go

У Restate уже есть **официальный Go‑SDK** [3]:

- Пакеты:
  - `encoding`,
  - `ingress`,
  - `rcontext`,
  - `server` (регистрация обработчиков),
  - `protoc-gen-go-restate` (плагин для генерации кода) и др. [3].
- SDK предоставляет:
  - API контекста (`Context`) с методами:
    - вызов других сервисов,
    - управление состоянием,
    - таймеры и т.д.,
  - кодогенерацию из `.proto`:
    - typed‑клиенты и server‑интерфейсы [3],
  - ingress‑SDK для внешних вызовов handlers [3].

**Что это значит для порта**:

- **Не нужно** заново придумывать клиентский API на Go — он уже есть и активно используется в примерах.
- Главное — чтобы **ваш Go‑сервер говорил на том же протоколе**, что и текущий Rust‑сервер:
  - те же REST/gRPC эндпоинты,
  - те же protobuf‑форматы запросов/ответов,
  - те же семантики durable execution и idempotency.

## 5. Пошаговый план портирования Restate‑Server на Go

### Шаг 1. Определить границы совместимости

1. Взять спецификации протокола из репо `restatedev/restate`:
   - `service-protocol`,
   - docs по HTTP/gRPC эндпоинтам.
2. Решить:
   - **Цель №1**: ваш Go‑сервер должен быть drop‑in‑заменой Rust‑сервера для SDK (в т.ч. Go‑SDK).
   - Это значит:
     - полностью совпадающие роуты и схемы сообщений,
     - те же semantics по durable execution и state.

### Шаг 2. Спроектировать модули Go‑сервера

Минимальный набор пакетов:

- `config` — загрузка и валидация конфигурации (yaml/toml/env).
- `metadata` — Raft‑контур и API для чтения/обновления метаданных.
- `log` — реализация Bifrost‑подобного сегментного лога.
- `state` — абстракция над Badger/Pebble.
- `partition` — воркеры, replay, вызов SDK‑обработчиков.
- `ingress` — HTTP/gRPC вход.
- `snapshots` — работа с S3/MinIO.
- `observability` — Prometheus + OpenTelemetry.
- `cli` — оболочка для запуска с нужными ролями.

### Шаг 3. Реализация Durable Execution

1. Внутреннее представление **invocation journal**:
   - каждая запись — «шаг»:
     - `InvokeStart`,
     - `StateRead/StateWrite`,
     - `CallStart/CallResult`,
     - `TimerSet/TimerFired`,
     - `InvokeCompleted / InvokeFailed`.
2. При вызове handler через Go‑SDK:
   - SDK не должен самостоятельно писать в диск — он отправляет операции на ваш сервер через протокол,
   - сервер:
     - записывает операцию в лог,
     - обновляет state‑кэш,
     - передаёт результат обратно SDK.
3. При рестарте:
   - partition worker читает журнал для конкретного invocationID,
   - проигрывает шаги, **пропуская уже завершённые**.

### Шаг 4. Согласованное состояние

- Для Virtual Objects/Workflows:
  - каждый handler вызывается с привязкой к ключу `K` → партиция `P(K)`,
  - worker партиции имеет **единоличный доступ** к состоянию `K`:
    - можно реализовать single‑thread‑loop на воркера, чтобы избежать сложной синхронизации.
- Все `GetState/SetState` handler’а должны:
  - логироваться как шаги,
  - применяться к Badger/Pebble с тем же последовательным порядком, что и в журнале.

### Шаг 5. Резервирование, фейловеры, снапшоты

- Организовать:
  - поток detection’а нод (health‑checks, госсип или pings),
  - выбор нового лидера партиции через Raft при падении старого,
  - `sealing` активного сегмента лога при пересменке.
- Снапшоты:
  - периодически инициировать snapshot‑процедуру для партиций
  - и обновлять `snapshotIndex` в метаданных.

### Шаг 6. Интеграция с Go‑SDK

- Проверить, что:
  - регистрация сервисов через Go‑SDK `server` пакет корректно соединяется с вашим ingress и partition‑воркерами,
  - ingress‑SDK для внешних вызовов (из других микросервисов) успешно взаимодействует с вашим API.

---

## 6. Практическая рекомендация по старту

Чтобы не «утонуть» сразу во всех деталях:

1. **Соберите упрощённый «одиночный» сервер на Go**:
   - без репликации и Raft,
   - один процесс, один лог, один worker,
   - HTTP‑ингресс и минимальная реализация durable execution для одного виртуального объекта.
2. Подключите **официальный Go‑SDK** и поднимите пример (например, ticket reservation из `examples`) [3]:
   - добейтесь, чтобы:
     - после «краша» процесса и перезапуска:
       - состояние и прогресс workflows сохранялись,
       - дубликатные вызовы с одним idempotency key не выполнялись повторно.
3. Затем постепенно добавляйте:
   - разделение на партиции,
   - репликацию логов,
   - Raft для метаданных,
   - снапшоты в S3.

---

## 7. Вывод

Restate — это не просто «ещё один workflow‑движок», а **лог‑центричная машина durable execution** с чётким разделением:

- **Ingress** → роутинг запросов и idempotency.
- **Лог (Bifrost)** → единый источник истины для всех событий и шагов.
- **Partition Processor** → исполнение логики и ведение KV‑состояния по ключу.
- **Control Plane (Raft)** → метаданные о партициях и ролях.
- **Снапшоты + объектное хранилище** → быстрый recovery.

При портировании на Go вам нужно **повторить именно эти свойства, а не синтаксис Rust‑кода**:

- главное — сохранить семантику durable execution, exactly‑once‑вызовов и одиночного писателя на ключ,
- и сделать runtime, совместимый с уже существующим Go‑SDK и протоколами Restate.

Если захочешь, можно дальше спроектировать конкретные интерфейсы пакетов (`log`, `metadata`, `partition`) или набросать skeleton‑код полноценного `main.go` с разбором ролей и запуском всех компонентов.
