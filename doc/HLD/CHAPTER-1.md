# Глава 1. Выбор Ядра: Почему Restate на Go?

**Важное уточнение:** Далее под «архитектурой Restate на Go» мы понимаем **нашу реализацию ключевых идей Restate** (durable execution, virtual objects, stateful proxy), а не точную репликацию оригинального Restate. В частности, мы используем Postgres вместо специализированного распределённого журнала — сознательный компромисс производительности ради простоты эксплуатации.

## 1.1. Дилемма 2026: Человек vs Агент

В мире оркестрации ИИ-процессов произошёл фундаментальный раскол. Выбор архитектурного фундамента (Engine) теперь зависит не от языка программирования, а от того, кто является истинным «владельцем» логики: Человек или Агент.

### Hatchet: Две парадигмы оркестрации

Hatchet поддерживает **две модели оркестрации**:

1. **Декларативные DAG-воркфлоу** для сценариев с заранее известной структурой
2. **Процедурную оркестрацию** через динамическое порождение дочерних задач во время выполнения

Для классических ETL-процессов или бизнес-сценариев с предсказуемой структурой идеально подходит DAG-подход. Однако для AI-агентов, которые действуют динамически, более естественна процедурная модель — когда агент может порождать новые задачи, организовывать циклы и условные ветвления прямо во время выполнения.

### Restate: Логика Агента как код

Restate предлагает концепцию **Durable Execution as Code**, где логика — это обычный код (if/else, while), а стейт-машина строится динамически на основе событий в журнале.

- **Virtual Objects:** «Бессмертные» объекты с встроенным KV-хранилищем, идеально подходящие для долгоживущих агентов с контекстом. В Restate они реализованы через собственное распределённое хранилище (RocksDB + снапшоты в object storage).
- **Журнал исполнения:** Полная трассировка всех действий агента для анализа и отладки
- **Модель программирования:** Близка к процедурному коду, который сегодня генерируют LLM — последовательный императивный код с ветвлениями и циклами

**Вердикт:** Для платформы Agentic AI архитектура Restate выигрывает благодаря:

- Естественной модели программирования для динамических агентов
- Встроенной поддержке долгоживущего состояния через Virtual Objects
- Полной трассируемости действий агента через event sourcing

## 1.2. Архитектурный донор: От комплексной платформы к Stateful Proxy

### Windmill: Полноценная платформа

Windmill — это комплексное решение, включающее workflow-движок, рантайм для скриптов, UI-конструктор и средства разработки. Хотя это фантастический продукт, создание аналогичного стека для наших нужд было бы избыточно сложным.

### Restate: Сфокусированный stateful proxy

Restate архитектурно концентрируется на ядре — **durable execution + stateful services**. Это stateful RPC-прокси с журналом исполнения, что идеально соответствует нашим требованиям.

**Ключевое отличие:** Оригинальный Restate использует собственный распределённый журнал (Bifrost) и KV-хранилище (RocksDB). В нашей Go-реализации мы сознательно идём другим путём.

**Наш подход на Go:**

- Высокопроизводительный сетевой сервис (HTTP/2, gRPC)
- **Postgres как универсальный durable backend** — компромисс производительности ради простоты развёртывания
- Один бинарник для любых окружений (от Raspberry Pi до K8s)

## 1.3. Технический базис: Event Log и Virtual Objects

### Event Sourcing для полной трассируемости

Вместо хранения статуса мы храним полный **журнал событий**:

1. `CallStarted(FunctionA)`
2. `Sleep(1000ms)`
3. `VariableSet("key", "value")`

При сбое система восстанавливает состояние через replay журнала, обеспечивая:

- **Гарантированное выполнение** — вызовы не теряются
- **Полную трассируемость** — видна вся цепочка решений агента
- **Легкую отладку** — можно «перемотать» выполнение в любой момент

### Virtual Objects: Наша реализация

В отличие от оригинального Restate с встроенным KV-хранилищем, мы реализуем Virtual Objects как:

- **In-memory структуры** для быстрого доступа
- **Периодические снапшоты в Postgres** для долговременного хранения
- **Восстановление из журнала событий** при рестарте
- **Изоляция по ключу** — состояние доступно только по ключу объекта

### Postgres как архитектурный выбор

В нашем Go-движке мы используем Postgres для:

- Очередей задач через `SELECT … FOR UPDATE SKIP LOCKED`
- Механизма блокировок (Advisory Locks)
- Долговременных снапшотов состояния
- Transaction outbox для интеграций

**Важно:** Это осознанный компромисс — Postgres даёт хорошие гарантийные свойства (ACID) и простоту администрирования, но проигрывает в пропускной способности и задержках специализированным системам типа оригинального Bifrost в Restate. При правильной настройке наша реализация обеспечивает p50 порядка десятков миллисекунд, но задержка растёт с увеличением нагрузки и размера журналов.

## 1.4. Сравнительный анализ: Компромиссы и ниши

| Характеристика | Temporal               | Inngest           | Hatchet             | Restate (наш подход) |
| :------------- | :--------------------- | :---------------- | :------------------ | :------------------- |
| **Модель**     | Workflow Engine        | Event-driven Push | DAG + Procedural    | Stateful Proxy       |
| **Стейт**      | В истории (Replay)     | В шагах (Memo)\*  | DAG + Runtime       | **Virtual Objects**  |
| **Latency**    | Зависит от сценария¹   | HTTP + Retry²     | gRPC, оптимизирован | **Десятки мс p50³**  |
| **Сложность**  | Высокая⁴               | Низкая            | Средняя             | **Средняя**          |
| **Идеал для**  | Транзакции, compliance | SaaS интеграции   | ETL, пайплайны      | **AI Агенты**        |

\*В Inngest состояние не живёт как отдельная «сущность с ключом», а хранится как результаты шагов конкретной функции; нет аналога Virtual Objects для произвольных долгоживущих агентов.  
¹ Temporal даёт сильные гарантии детерминированности, за что в сложных сценариях может возникать дополнительная задержка  
² Inngest использует HTTP с ретраями, но также поддерживает режимы Connect (WebSocket) и Checkpointing для снижения латентности  
³ Наша реализация обеспечивает десятки миллисекунд p50 при правильно настроенном Postgres; задержка растёт с нагрузкой и размером журналов  
⁴ Высокая сложность ментальной модели (детерминизм, ограничения workflow)

### Почему не другие решения?

**Inngest:** Отличный выбор для event-driven интеграций. При self-hosted варианте вы отвечаете за развёртывание и доступность endpoint'ов. В нашем контексте stateful-proxy модель Restate обеспечивает лучшую изоляцию и контроль над выполнением.

**Temporal:** Остаётся стандартом для сложных workflow, но требует дисциплины детерминированного кода. Для динамичных AI-агентов модель Restate психологически проще и ближе к обычному программированию.

**Hatchet:** Поддерживает как DAG, так и процедурную оркестрацию, но Virtual Objects в Restate дают более естественную абстракцию для долгоживущих агентов с состоянием.

### Компромиссы по производительности

Каждая система делает свои trade-offs:

- **Temporal** — богатые абстракции vs потенциальная дополнительная задержка
- **Restate/Hatchet** — оптимизированы для низкой задержки через легкие RPC
- **Inngest** — гибкость event-driven модели vs зависимость от инфраструктуры
- **Наш подход** — простота развёртывания (Postgres) vs максимальная производительность

## 1.5. Итог Главы 1: Обоснованный выбор с ясными компромиссами

Мы выбираем архитектуру, **вдохновлённую Restate**, но адаптированную под практические потребности:

1. **Go-реализация** для производительности и кроссплатформенности
2. **Postgres как бэкенд** вместо специализированного журнала — сознательный компромисс простоты vs производительности
3. **Virtual Objects** как ключевая абстракция для агентов с памятью
4. **Event sourcing** для полной трассируемости и восстановления

**Что это даёт:**

- Гибкую модель программирования для динамичных агентов
- Stateful-сущности «из коробки» с изоляцией по ключу
- Простое развёртывание (один бинарник + Postgres)
- Хорошую основу для интеграции с UI Windmill

**Чего это стоит:**

- Производительность ниже, чем у оригинального Restate с Bifrost
- Зависимость от Postgres как критического компонента (потребуются репликация и отработанные сценарии failover)
- Необходимость ручного управления миграциями и бэкапами

**Итоговый вердикт:** Для Agentic AI-платформы в 2026 году наш подход предлагает оптимальный баланс между мощностью абстракций (Virtual Objects, durable execution), простотой реализации (Go + Postgres) и эксплуатационной практичностью. Мы осознанно выбираем проверенные технологии и честно говорим о компромиссах, создавая решение, которое можно реально использовать в production.
