# Глава 3. Среда Исполнения (Runtime): Стратегия "Полиглот"

## 3.1. Главная дилемма: Кто выполняет код?

Архитектура Restate (наш донор для движка) — это движок долговременного выполнения (Durable Execution) и оркестратор. Сам сервер не содержит встроенного Python‑рантайма и не выполняет произвольный Python‑код «внутри себя», но через Python‑SDK позволяет подключать отдельные Python‑сервисы, в которых этот код исполняется. Windmill решает задачу нативного запуска Python‑кода через мощную подсистему воркеров и интеграцию с Docker/оркестраторами. Нам не нужен столь же сложный уровень абстракции внутри самого движка, поэтому мы выбираем более лёгкую модель multi‑runtime.  
Для нашего продукта нам нужно решение, которое сочетает безопасность с простотой эксплуатации.

---

## 3.2. Спектр решений (The Runtime Spectrum)

Мы не можем выбрать одну технологию на все случаи жизни. Разным типам агентов нужны разные среды.

### Вариант A: Управление контейнерами на хосте — Стандартный подход

Это подход, похожий на то, как большинство CI/CD систем и оркестраторов (включая Flyte) запускают задачи в контейнерах: движок управляет Docker/OCI‑контейнерами на хосте (часто через Docker socket или эквивалентный runtime).

- **Как работает:** Наш Go‑движок имеет доступ к Docker Socket хоста. Когда нужно запустить шаг воркфлоу, он создает новый контейнер из образа (например, `python:3.11-slim`).
- **Плюсы:**
  - **Совместимость:** Работает любой Python‑код, любые `pip` пакеты (Pandas, Numpy, LangChain).
  - **Простота:** Понятно любому разработчику.
- **Минусы:**
  - **Холодный старт:** Запуск контейнера занимает 1–3 секунды при тёплом образе и без сети; время может увеличиться до 3–10+ секунд при первом pull тяжёлых ML‑образов.
  - **Ресурсы:** Каждый контейнер потребляет значительный объём памяти (типично ~150–300 МБ RSS под реальную нагрузку; на Linux overhead ниже, на macOS/Windows через Docker Desktop — выше). На одном сервере сложно запустить 1000 агентов одновременно.
  - **Безопасность:** Доступ к `/var/run/docker.sock` фактически даёт процессу root‑права на хосте, что создаёт серьёзные риски. В индустрии это считается security smell, и рекомендуется использовать альтернативы: rootless‑Docker, Podman (который изначально работает без демона и лучше вписывается в модель «без root‑daemon»), отдельные хосты под Docker‑воркеры или дополнительные слои изоляции (gVisor, Firecracker).

### Вариант B: Встроенный Wasm (Wazero) — Инновация

Это тот же класс подхода, который используют edge‑платформы (Cloudflare, Fastly): выполнение изолированных пользовательских модулей (часто Wasm) внутри общего процесса.

- **Как работает:** Код агента (написанный на Go, Rust или AssemblyScript) компилируется в `.wasm` и запускается **внутри** нашего процесса Go с помощью библиотеки `wazero`. Компиляция модуля выполняется один раз при старте и может занимать сотни миллисекунд, но инстанцирование заранее скомпилированного модуля для малых и средних размеров часто укладывается в десятки–сотни микросекунд (вплоть до <1 мс при оптимизации).
- **Плюсы:**
  - **Скорость:** Быстрый старт (инстанцирование <1 мс для небольших модулей) и возможность предоптимизации через инструменты вроде Wizer.
  - **Безопасность:** Жёсткая изоляция памяти и контролируемый доступ к ресурсам через ограниченный набор импортов. Модуль не может выйти из песочницы без явно предоставленных хост‑функций.
  - **Легкость:** Тысячи агентов потребляют минимум памяти, особенно при жёстком ограничении памяти через конфигурацию рантайма.
- **Минусы:**
  - **Сложность:** Python в Wasm требует сборки CPython под WASI (официально поддерживается с PEP 816) и продуманного доступа к файловой системе и окружению. Чистый Python работает стабильно, но C‑расширения (например, NumPy, pandas) нуждаются в специальной сборке (Pyodide/WASI‑сборки), а тяжёлые библиотеки типа `torch` остаются сложными для портирования и в основном доступны только для инференса через WASI‑NN.
  - **Производительность:** Python‑код, запущенный через Wasм (Pyodide/CPython‑WASI), обычно в 3–5 раз медленнее нативного выполнения (для чистого Python‑кода; для операций с NumPy разница может быть меньше, но всё же заметна). **Рекомендуем Wasm‑режим для бизнес‑логики и лёгкого ETL, но не для тяжёлых ML‑задач с PyTorch/TensorFlow; их лучше запускать в Docker или через Remote/A2A.**

### Вариант C: Внешние Агенты (External via A2A)

Это подход «Без хостинга».

- **Как работает:** Мы вообще не запускаем код агента. Мы используем **A2A (Agent‑to‑Agent)** протокол (реализуемый обычно через REST/gRPC с обязательной корреляцией вызовов и идемпотентностью) для отправки задачи во внешний сервис (например, агенту на платформе AutoGPT или кастомному микросервису клиента).
- **Плюсы:** Нулевая нагрузка на нашу инфраструктуру. Мы только оркестрируем.
- **Минусы:** Сетевая задержка, необходимость аутентификации, управления тайм‑аутами/повторными попытками, а также мониторинга SLA внешних агентов.

## 3.3. Гибридная Стратегия: "Multi‑Runtime"

Для коммерческого успеха мы должны предложить клиентам **градацию режимов**:

| Режим        | Технология        | Для чего подходит                                               | Целевая аудитория                              |
| :----------- | :---------------- | :-------------------------------------------------------------- | :--------------------------------------------- |
| **Lite**     | **Wasm (Wazero)** | Простая логика, роутинг, фильтрация данных, вызовы API.         | Инженеры, которым нужна максимальная скорость. |
| **Standard** | **Docker**        | Тяжёлые агенты с библиотеками (RAG, PDF parsing, Data Science). | Data Scientists, ML‑инженеры.                  |
| **Remote**   | **HTTP / A2A**    | Подключение готовых агентов, живущих в других облаках.          | Enterprise‑интеграторы.                        |

### Как это выглядит в продукте?

Пользователь в UI выбирает тип шага:

1.  _«Script (Python)»_ → Запускается в Docker.
2.  _«Logic (Wasm)»_ → Запускается мгновенно в процессе.
3.  _«External Agent»_ → Идет сетевой вызов.

Наш движок на Go прозрачно маршрутизирует задачи в нужный рантайм, сохраняя единый лог выполнения и состояние Durable Execution. Это делает платформу универсальной: мы быстры там, где это возможно, и совместимы там, где это необходимо.

**Ключевые технические требования для реализации:**

- **Общий контракт ввода/вывода:** Независимо от рантайма каждый шаг должен принимать и возвращать данные в едином формате (например, JSON‑схема).
- **Централизованное логирование и мониторинг:** Логи и метрики собираются на уровне оркестратора, а не внутри конкретного рантайма.
- **Управление ресурсами:** Для Docker‑шагов — кэширование образов, установка лимитов CPU/памяти; для Wasm‑шагов — жёсткие лимиты памяти (через `WithMemoryLimitPages`, `RuntimeConfig`) и контроль максимального размера heap, чтобы запуск тысяч агентов не перегрузил хост.
