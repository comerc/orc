# Глава 2. Паттерны Надежности в мире ИИ

## 2.1. Транзакции и Саги: Укрощение хаоса LLM

Классические ACID-транзакции (commit/rollback) неприменимы в мире ИИ. Нельзя «откатить» генерацию текста или вызов внешнего API (отправленное письмо). В сценариях, где участвуют внешние эффекты (письма, платежи, LLM‑вызовы), целостность на уровне бизнес‑процесса удобнее всего обеспечивать через паттерн **Saga** (Сага) [1][3].

### Проблема LLM

ИИ-агент — это вероятностная сущность.

- Он может сгенерировать правильный ответ.
- Он может сгенерировать мусор.
- Он может зависнуть.

Если агент на шаге 3 ошибся, нам нужно не просто «упасть с ошибкой», а запустить цепочку **компенсирующих действий** (например, извиниться перед пользователем, отменить бронь в календаре, вернуть токены на баланс) [3][4]. Важно понимать, что компенсации — это такие же полноценные шаги, которые должны быть идемпотентными, могут требовать повторных попыток и собственной обработки сбоев. Кроме того, хотя нельзя «откатить» уже отправленные пользователю данные, можно отменить дальнейшую генерацию, чтобы минимизировать затраты и побочные эффекты.

### Решение: Orchestrated Saga (Код с компенсациями)

В некоторых системах (например, Hatchet) саги часто рисуются как ветвления на графе («Если ошибка → иди в ветку Б»). Это может сделать граф гигантским и нечитаемым.  
В архитектуре, подобной Restate, мы реализуем Сагу через **список компенсаций**, которые выполняются в обратном порядке при ошибке [1][2].

**Как это выглядит в коде агента (Go) — пример в стиле Restate:**

```go
func RunAgent(ctx restate.WorkflowContext) (res Result, err error) {
    var compensations []func() error

    defer func() {
        if err != nil {
            // Выполнить компенсации в обратном порядке
            for i := len(compensations) - 1; i >= 0; i-- {
                if cErr := compensations[i](); cErr != nil {
                    // логируем, при необходимости эскалируем
                    err = cErr
                }
            }
        }
    }()

    // Шаг 1: резервируем ресурсы
    _, err = restate.Run(ctx, func(ctx restate.RunContext) (restate.Void, error) {
        return ReserveResources()
    }, restate.WithName("reserve"))
    if err != nil { return }

    compensations = append(compensations, func() error {
        _, cErr := restate.Run(ctx, func(ctx restate.RunContext) (restate.Void, error) {
            return ReleaseResources()
        }, restate.WithName("release_resources"))
        return cErr
    })

    // Шаг 2: вызов LLM (с ретраями согласно политике)
    _, err = restate.Run(ctx, func(ctx restate.RunContext) (LLMResponse, error) {
        return CallLLM()
    }, restate.WithName("llm_generate"), restate.WithRetryPolicy(/* политика ретраев */))
    if err != nil { return }

    return
}
```

**Преимущество:** Разработчик пишет линейный код («счастливый путь»), а обработку «грязной работы» по откатам берет на себя движок. Движок гарантирует, что каждая компенсирующая функция будет выполнена, даже если сервер упадет посередине процесса отката. В реальных системах (например, Temporal, AWS Step Functions, Azure Durable Functions) при необработанной ошибке движок переводит выполнение в ветку/блок, где разработчик разместил компенсации, и гарантирует выполнение этой ветки с учётом ретраев и восстановления после падений [2][5]. Каждый шаг и компенсация должны быть идемпотентны, так как движок может переисполнить их после сбоя.

## 2.2. Точка входа: От Ingress SDK к AI Gateway

Как запустить процесс? В классическом Restate используется Ingress SDK — специальный клиент, который обеспечивает идемпотентность запуска, трассировку и конфигурацию ретраев [1]. Для ИИ-платформы этого мало. Нам нужен полноценный **AI Gateway**.

### Эволюция входа

- **Ingress SDK (Restate):** Обеспечивает идемпотентность запуска, трассировку и управление ретраями. «Не запускай процесс №123 дважды».
- **AI Gateway (Наш продукт):** Это умный шлюз перед запуском воркфлоу, аналогичный решениям Kong AI Gateway, Gloo AI Gateway и другим современным AI-шлюзам [6][7][8].

### Функции Gateway

1.  **Semantic Caching:** Перед тем как будить агента и тратить деньги, Gateway проверяет: «Мы уже отвечали на похожий вопрос?». Если да — ответ отдается мгновенно из кэша (Redis/Vector DB). При этом требуется настройка порога сходства (similarity threshold) и стратегии инвалидации кэша (например, при обновлении знаний или смене версии модели) [5][7]. Для чувствительных доменов (медицина, финансы) кэш может быть отключён или строго регулируем; нередко кэш хранят отдельно и включают только для ответов, прошедших дополнительную проверку (manual review или автоматическую валидацию).
2.  **Rate Limiting & Quotas:** «Отдел маркетинга исчерпал бюджет на GPT-4». Gateway блокирует запрос еще до старта Durable-процесса. В современных AI-шлюзах квоты часто рассчитываются по **токенам** (и, соответственно, стоимости), а не только по количеству запросов [8][10]. Это стандартная функция в таких решениях, как Kong, Apigee, Azure API Management. При этом бухгалтерия и биллинг часто реализуются отдельным сервисом, который читает usage‑метрики от шлюза.
3.  **Model Routing:** Gateway может на лету подменить модель. Если GPT-4 недоступна, он направит запрос в Claude 3.5 или локальную Llama, передав этот параметр в контекст агента [6][9]. При этом Gateway должен гарантировать совместимость формата ответа, используя адаптеры для нормализации вывода к единому контракту.
4.  **Безопасность и аудит:** Для enterprise-клиентов критически важны аутентификация, авторизация, а также аудит запросов и затрат [8][10].

**Итог:** Мы не просто «запускаем скрипт», мы управляем потоком запросов. Это критически важная фича для продажи Enterprise-клиентам. Подобные возможности реализуются в современных решениях, таких как Kong AI Gateway и других API-шлюзах с поддержкой semantic cache [6][7][8].

## 2.3. Durable Streams: Разделение ответственности

В ИИ-приложениях есть фундаментальный конфликт между надежностью бэкенда и ожиданиями пользователя.

- **Бэкенд:** «Я буду думать 5 минут, чтобы дать лучший ответ».
- **Пользователь:** «Я хочу видеть хоть что-то прямо сейчас».

### Проблема WebSocket

Обычный стриминг токенов (через WebSocket) хрупок. Если у пользователя мигнул Wi-Fi, соединение рвется, и он видит ошибку сети, хотя на сервере агент продолжает работать и тратить деньги [11][12].

### Решение: Архитектура Durable Streams

Мы разделяем процесс на два независимых потока, следуя подходу, аналогичному протоколу Durable Streams [10][11]:

1.  **Execution Stream (Server-side):** Агент работает и пишет свои «мысли» (токены, логи, reasoning) в надежный лог (append-only log в Postgres/Redis/специализированных системах, таких как Kafka или Redis Streams). Ему все равно, слушает ли его кто-то. На практике токены часто буферизуются и записываются чанками для оптимизации, а для лога устанавливается TTL (Time To Live) или применяется компакция, чтобы не хранить данные вечно [13][14].
2.  **Delivery Stream (Client-side):** UI клиента подключается к этому логу через транспорт (WebSocket, SSE, HTTP‑polling). Для обеспечения мультиклиентского доступа и управления backpressure используются механизмы consumer groups (например, в Redis Streams или Kafka) [13][14]. Для LLM-стриминга сегодня часто предпочитают **SSE** (Server-Sent Events) как более простой и надежный вариант [12][15]. При большом количестве подписчиков и высоком throughput дополнительно требуется контроль скорости записи и чтения (throttling), чтобы не переполнить хранилище и не убить UI.
    - Если связь есть — он читает в реальном времени.
    - Если связь пропала — клиент запоминает последний полученный `offset` (смещение), который может храниться локально (localStorage) или на сервере, привязанным к `session_id`.
    - Когда связь вернулась — клиент просит: «Дай мне всё, что случилось после offset X».

**Результат:** Пользователь получает **Gap-less UX** (бесшовный опыт). Он может закрыть вкладку, уйти пить кофе, открыть с телефона — и увидеть полную историю генерации без пробелов [11][13]. Это и есть уровень качества, который отличает профессиональный инструмент от поделки на коленке. Durable Streams обеспечивают уровень хранения и согласованности, в то время как транспортные механизмы отвечают за доставку, что вместе даёт отказоустойчивый стриминг для LLM. Практически всегда нужен токен доступа (JWT/API‑key), который проверяется при каждом запросе к стриму, особенно в multi‑tenant окружениях.

---

**Итог главы:** Описанные паттерны — **Saga**, **AI Gateway** и **Durable Streams** — соответствуют современным практикам построения надёжных ИИ-систем и реализованы в таких решениях, как Temporal, Restate, Kong AI Gateway и протоколе Durable Streams. Их применение позволяет создавать отказоустойчивые, масштабируемые и удобные для пользователя ИИ-приложения enterprise-уровня.
